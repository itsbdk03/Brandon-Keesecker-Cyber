PUBLIC SAFE / INDEPENDENT SECURITY LABS

Built to explain
the security decision.

These seven independent learning projects pair working browser software with assessment logic, transparent detection rules, and defensible limitations. The aim is to demonstrate how cybersecurity findings become evidence, investigation steps, architecture decisions, and remediation priorities.

Every case study now includes a four-stage architecture data flow, implementation file links, engineering decisions, limits, and a summary of automated verification. Review public GitHub verification ↗

01 // GRC ENGINEERING

ControlTrace

Launch workbench ↗

Problem: A control may appear “implemented” while lacking clear ownership, evidence references, or a testable narrative. ControlTrace models the handoff between policy language and audit-reviewable documentation.

NIST 800-53EVIDENCE TRACEABILITYAUDIT REPORT
Working features
  • Nine editable fictional controls with status, owner, narrative, evidence, and gap.
  • Search, filtering, status dashboard, and local persistence.
  • Quality cross-check for records marked ready without documentation.
  • CSV export and written audit-brief generation.
Engineering / risk decisions
  • Preserve source narratives instead of inventing compliance outcomes.
  • Do not claim the program selector changes the authoritative baseline.
  • Separate documentation readiness from tested control effectiveness.
  • Show incomplete records and remediation queues openly.
02 // BLUE TEAM DETECTION

SignalHunt

Launch workbench ↗

Problem: A single log match is not a security incident. SignalHunt walks analysts from raw synthetic events through deterministic detection rules and cross-event correlation, then documents an investigation narrative.

AUTH TELEMETRYT1110T1078T1059
Working features
  • Import and validate local CSV or JSON logs, bounded to 10,000 events.
  • Detect repeated failures, subsequent login, scripting activity, and watchlisted egress.
  • Correlate the initial authentication sequence by identity and source IP; later activity is temporal context only.
  • Timeline, event search, analyst JSON export, and Markdown case narrative.
Engineering / risk decisions
  • Rule matches are triage leads; contextual analysis is mandatory.
  • MITRE ATT&CK labels are illustrative associations, not certainty.
  • Source fields are treated as plain text rather than executable markup.
  • Logs are processed in browser memory, without uploading.
03 // CLOUD ARCHITECTURE

CloudGuard

Launch workbench ↗

Problem: Security recommendations are easier to understand when mapped to a system boundary, its dependencies, and data flows. CloudGuard gives visitors a way to experiment with defense in depth.

IAMENCRYPTIONSEGMENTATIONTELEMETRY
Working features
  • Interactive architecture with six enable/disable safeguards.
  • Example security posture, gaps, and contextual recommendations.
  • Federal and DoD demonstration scenarios.
  • Downloadable architecture review with enabled and missing measures.
Engineering / risk decisions
  • Illustrative risk points are not measured probabilities or FedRAMP scores.
  • Defense controls are not proven effective by flipping a switch.
  • Real authorization needs actual evidence, testing, and agency processes.
04 // RISK MANAGEMENT

RiskMatrix

Launch workbench ↗

Problem: A risk register is useful only if teams can decide what to treat first and explain why. RiskMatrix makes risk scoring and mitigation assumptions visible rather than hiding the formula.

RISK REGISTER5 × 5 HEATMAPPRIORITIZATION
Working features
  • Create and remove fictional risks, with owners and inherent scoring.
  • Adjust mitigation maturity and observe residual change.
  • Filter using a clickable risk heat map.
  • Rank treatment priorities; export CSV or risk committee memo.
Engineering / risk decisions
  • The weighting is a declared toy model, not an official NIST method.
  • Treatment decisions still require owner, approval, context, and review date.
  • Users can trace the calculated residual score to the inputs.
05 // AWS SECURITY ANALYSIS

ConfigLens

Launch workbench ↗

Problem: Infrastructure snapshots can contain obvious configuration exposures, but findings need to be explainable and reproducible. ConfigLens scans a documented JSON schema against twelve explicit checks.

AWS S3IAMSECURITY GROUPSCLOUDTRAILRDS / EBSSARIF 2.1.0
Working features
  • Exposed and hardened scenarios with different expected findings.
  • Inspect S3 access and transport, IAM wildcards, admin-port ingress, CloudTrail, data encryption, and root MFA.
  • Evidence-based findings with resource names and remediation guidance.
  • Severity filters, JSON import, analyst Markdown report, and SARIF export.
Engineering / risk decisions
  • Missing properties are “not evaluated,” never silently passing.
  • Rules inspect the displayed summary—not Terraform/HCL or AWS APIs.
  • A 100% sample pass rate cannot establish real cloud security.
  • Links go to AWS documentation, not unverified compliance claims.
06 // DEFENSIVE THREAT MODELING

AttackPath

Launch workbench ↗

Problem: A static network diagram rarely explains which trust relationships expose protected systems or how individual safeguards disrupt modeled access paths. AttackPath demonstrates deterministic defensive graph traversal over fictional infrastructure.

GRAPH TRAVERSALDEFENSE IN DEPTHCOUNTERFACTUAL MODELINGAUTOMATED TESTS
Working features
  • Three fictional scenario presets with user-adjustable defensive safeguards.
  • Directed graph reachability, target path analysis and modeled interrupted transitions.
  • Prioritized safeguard interventions based on the number of routes interrupted.
  • Source-backed executive report, raw JSON export and technical workpaper.
Engineering / risk decisions
  • Compute reachable graph routes from explicit assumptions; never claim an actual exploit.
  • Describe blocked transitions as modeled outcomes, not proof that a system is secure.
  • Keep topology, weakness conditions and result calculation separately testable.
  • Expose scope omissions, alternative pathways and other modeling limits.
07 // SECURITY DOCUMENTATION AUTOMATION

AssuranceFlow

Launch workbench ↗

Problem: Security documentation can look complete despite lacking accountable owners, evidence identifiers or testable implementation narratives. AssuranceFlow provides a transparent quality-check workflow for fictional control records and deliberately bounded OSCAL-style inputs.

CONTROL DOCUMENTATIONOSCAL SSP SUBSETINPUT VALIDATIONEVIDENCE QUALITY
Working features
  • Eight fictional, editable control records with ownership, narratives, evidence references and remaining actions.
  • Explainable completion heuristic with prioritized review gaps.
  • Bounded JSON import, partial SSP implemented-requirements description import and output.
  • Markdown reviewer export, local JSON workpaper and print-ready executive report.
Engineering / risk decisions
  • Separate record completeness from tested security effectiveness.
  • Leave imported evidence and ownership fields unknown when source data lacks proof.
  • Keep a narrow compatibility claim rather than suggesting a full OSCAL validator.
  • Use isolated, synthetic data with no customer evidence or browser-to-server upload.
Security and professional ethics

All bundled configurations, system records, event logs, and risk scenarios are synthetic. No Coalfire or client evidence, CUI, PHI, credentials, production logs, or protected customer data are used. These applications are portfolio demonstrations and must not be represented as official FedRAMP, DoD, HITRUST, HIPAA, or SOC 2 assessors or certification engines.
